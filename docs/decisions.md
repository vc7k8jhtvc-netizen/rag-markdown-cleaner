# DEC-001 使用本地工作目录模型

日期：待补充

状态：已采用

背景：程序需要管理配置、提示词、输入、输出、日志、复核文件、批次状态和运行控制文件。

问题：这些相关文件需要使用稳定且一致的路径边界，供处理、缓存、恢复和安全校验共同使用。

考虑方案：

方案A：配置、输入、输出和运行状态统一放在同一个 base directory。

方案B：待补充。

最终决定：配置、提示词、输入、输出、日志、复核文件和控制文件统一来自同一个 base directory。

选择原因：统一目录使相关路径共享同一安全边界，并允许工作目录整体迁移；其他历史原因待补充。

影响：工作目录可以整体迁移；只复制部分文件可能破坏批次恢复、缓存身份和运行状态之间的关系。

# DEC-002 通过 HTTPX 直接调用兼容接口

状态：已采用

问题：需要选择接口调用方式，同时控制项目对特定服务提供方的耦合。

考虑方案：

方案A：使用 HTTPX 直接调用兼容接口。

方案B：使用特定提供方的 SDK。

影响：项目可以兼容多个实现相同协议的接口，但需要自行处理不同提供方的响应差异和兼容限制。

# DEC-004 不能安全拆分时停止规划

日期：待补充

状态：已采用

背景：Markdown 可能包含 fenced/indented code、表格、列表、引用和 Front Matter 等不能随意切断的结构。

问题：不可安全拆分的结构超过分片限制时，需要在保持结构完整与强制满足大小限制之间作出选择。

考虑方案：

方案A：停止规划，要求调整限制或人工预处理。

方案B：在大小边界强制切断结构。

最终决定：保留 Markdown 结构；不可分结构超过限制时停止规划，不进行强制切断。

选择原因：避免为了继续处理而静默生成结构已损坏的 Markdown；其他取舍过程待补充。

影响：部分文件需要调整安全上限或人工预处理，但程序不会静默破坏不可安全拆分的结构。

# DEC-005 使用哈希和 metadata 定义缓存身份

日期：待补充

状态：已采用

背景：长文档处理可能跨多次运行，需要复用已经完成且仍然有效的分片和完整结果。

问题：缓存必须能够识别源文件、提示词、模型、端点、校验模式或输出内容发生的变化。

考虑方案：

方案A：使用内容哈希和完整 metadata 身份判断缓存。

方案B：待补充。

最终决定：只有源、分片、提示词、模型、端点、校验模式、规范策略、分片布局和输出哈希匹配时才复用结果。

选择原因：避免把配置或内容不一致的旧结果误认为有效缓存；其他方案评估待补充。

影响：缓存复用较为保守；内容或配置变化会使相关缓存失效，但降低了错误复用风险。

# DEC-006 先保存分片再组装完整文件

日期：待补充

状态：已采用

背景：单个文档可能包含多个耗时的 API 分片任务，运行过程中可能暂停、停止或发生网络中断。

问题：需要保存已经完成的工作，并确保只有全部有效分片才能形成完整文件。

考虑方案：

方案A：每个分片通过校验后独立保存，再组装完整文件。

方案B：待补充。

最终决定：每个通过校验的分片独立保存；所有预期分片有效后再合并完整文件。

选择原因：支持长任务复用已经完成的分片和批次恢复；其他历史原因待补充。

影响：中断后可以从已验证分片继续；partial 响应只用于诊断，对应分片仍需重新请求。

# DEC-007 验证后发布并采用原子写入

日期：待补充

状态：已采用

背景：输出文件、metadata 和批次状态可能在写入、校验或组装过程中失败。

问题：需要防止半写入内容成为正式结果，并避免失败的新候选结果破坏已有有效文件。

影响：写入和发布流程更安全，但需要维护临时文件、替换和回滚逻辑。

# DEC-008 默认严格校验并保留显式宽松模式

日期：待补充

状态：已采用（2026-07-29 更新）

背景：不同输入和模型输出对 YAML Front Matter 的完整性支持可能不同。

问题：需要在强制统一格式与兼容缺少或不完整 Front Matter 的结果之间确定校验策略。

考虑方案：

方案A：默认使用兼容模式，并允许用户显式启用严格校验。

方案B：默认或始终使用严格校验。

最终决定：默认使用严格模式；`--no-strict` 可显式启用兼容旧输入的宽松模式。宽松模式的最终结果不得自动批准入库。

选择原因：Front Matter 是下游索引的结构化输入，默认允许损坏格式发布会把格式风险转移到入库阶段；显式宽松模式仍保留旧输入兼容能力。

影响：新任务默认阻止缺失或损坏 Front Matter 的第一分片。最终结果使用 `processed`、`review_required` 和 `approved_for_ingestion` 区分技术完成、复核要求与可入库状态；旧 `completed` 结果需要重新组装分类，但不会重复调用已完成分片的 API。

# DEC-009 使用启发式质量门槛并保留人工复核

日期：待补充

状态：已采用

背景：模型输出可能出现明显删减、扩写或结构损失，但自动程序无法可靠证明法规和技术内容的语义正确性。

问题：需要决定哪些风险自动阻断、哪些风险交由人工复核，以及自动检查是否可以作为最终验收。

考虑方案：

方案A：使用启发式门槛阻断严重问题，并将普通风险交给人工复核。

方案B：依赖自动检查直接完成最终验收。

最终决定：严重长度或扩写异常、受保护正文中的数字/单位/标准编号/URL 变化，以及正文稳定锚点大量丢失，默认阻止保存或发布，并保留失败候选供人工检查。允许删除的广告行不参与受保护值和锚点比较。用户明确确认且候选指纹仍匹配时，可以将该候选转为完成分片。普通风险进入 `review/`，自动检查不作为语义正确性的最终证明。

选择原因：现有检查能够识别部分明显异常，但不足以替代人工判断；原始阈值选择过程待补充。

影响：明显损失、扩写、关键值变化和大范围正文替换可以自动拦截；质量策略版本变化会使已有缓存按新规则重新校验。自动门槛误报时，用户可在留下确认记录的前提下继续组装。法规、技术内容和最终可用性仍需人工验收，不支持仅凭 `review_required=false` 无人值守入库。

# DEC-014 运行数据按生命周期保留且不按时间自动删除

日期：2026-07-28

状态：已采用

背景：`logs/`、`review/`、`*.partial.md`、失败候选和批次 manifest 分别承担审计、人工复核、故障诊断和断点恢复职责，其中可能包含教材内容、本机路径或其他不适合公开的数据。

问题：需要在可恢复性、诊断价值、存储空间和数据保护之间确定明确边界，同时避免程序自动清理造成不可恢复的数据丢失。

考虑方案：

方案A：按生命周期保留；程序只在成功提交替代结果后清理已完成使命的诊断副本，不按固定天数或磁盘压力删除。其他清理由用户在任务完全停止、依赖关系确认、独立备份完成并验证后明确决定。

方案B：按固定天数自动删除日志、复核文件、partial 和旧 manifest。

最终决定：采用方案A。源码由 Git 保存；运行数据使用工作目录之外的受控备份。备份至少覆盖 `input/`、`output/`、`review/`、`logs/` 和 `prompt.md`；`.env` 必须单独加密保存或通过安全配置重新建立，不得进入普通归档或 Git。

保留边界：

- `logs/batch.jsonl`、`logs/batches/` 和选择清单：至少保留到相关批次不再需要继续、重试或审计，并且最终结果备份已经验证。`latest.json` 与其引用的 manifest 必须作为一组保留。
- `review/`：保留到人工复核完成、结果被接受或明确放弃，并且接受后的输出已经备份。重新处理后不再需要复核时，程序会清理对应旧复核副本。
- `*.partial.md` 和失败候选：保留到失败原因确认、对应分片成功重试或明确放弃诊断，并且不再需要人工比较。对应分片成功提交后，程序会清理已经被完整结果替代的诊断文件。
- `output/` 中的有效分片和 metadata：只要仍可能重新组装、继续批次或避免重复 API 调用，就必须保留。

清理约束：程序不得按固定时间或磁盘压力自动删除上述数据。程序内置清理只能发生在替代结果已经成功提交且相关生命周期已经结束时。人工清理前必须确认任务已经退出、没有仍需恢复的批次、备份可读且包含所需文件；不得只删除 manifest、metadata 或复核报告中的一半。任何批量删除仍需单独确认。

选择原因：生命周期条件比固定天数更能反映断点恢复、复核和诊断需求；保守默认值可以避免误删教材、已付费生成结果和恢复状态。

影响：项目只会清理已被成功结果替代的诊断或复核副本，不会按时间全面回收运行数据空间；用户需要定期检查容量并在验证备份后决定其他清理。仅备份 Git 仓库仍不能恢复批次和用户资料。
